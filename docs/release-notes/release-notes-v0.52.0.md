# v0.52.0 – three-day price forecast

The *Spot price with forecast* sensor now carries Wolta's forecast for up to three days ahead, like wolta.se does, instead of tomorrow only. It is still information only: it never affects the optimisation grade, the economics or anything the integration uploads.

- **Forecast for days 2 and 3.** In `sensor.wolta_spot_price_with_forecast` the `prices` attribute now also holds forecast points for the two days after tomorrow, in time order with no timestamp repeated. Forecast points have `forecast: true` and a new `horizon`: `1` is tomorrow, `2` the day after tomorrow, `3` the day after that (the values follow the server, currently 1 to 3). Published prices have no `horizon`. Once tomorrow's prices are out (normally around 13:00) they replace tomorrow's forecast, so the forecast then starts at the following day. The list may hold fewer than three forecast days.
- **If a template treats all `forecast: true` points as tomorrow, filter on `horizon == 1`.** Before this version every forecast point was tomorrow's; now days 2 and 3 are in the list too. This includes the EMHASS example in the README: `prices` can now run well past 96 quarters, so keep the slice at the end of the template.
- **Uncertainty grows with distance.** A forecast two or three days out rests on weather forecasts that are further away, so it is less certain than tomorrow's. Use it for the rough shape of the coming days, not for single quarters.
- **New attribute `forecast_days`.** Each day has its own issue time and accuracy. `forecast_days` lists them for days 2 and 3 as `{date, horizon, issued_at, accuracy}`, without the points (those are in `prices`). `forecast_issued_at` and `forecast_accuracy` are unchanged and still describe tomorrow's forecast. `forecast_days` is an empty list when there is no forecast for those days.
- **Accuracy is per horizon.** `upstream_mae_ore_kwh` is the predictor project's backtest error for that horizon: roughly 18–26 öre/kWh for tomorrow and about 21–29 öre/kWh for days 2 and 3 across SE1–SE4 at current rates. It was measured with actual weather, so the real-world error is larger, more so for days 2 and 3. `basis: wolta` needs 14 measured days per horizon, so days 2 and 3 show `basis: upstream` for a while.
- **One extra request, only when you use it.** The integration fetches the later days from the public Wolta price endpoint once per poll, alongside the price request, and only while *Spot price with forecast* is enabled. With that sensor disabled (the default), or for the plain *Spot price* sensor, nothing is requested that was not before. If the extra request fails, the sensor keeps today, tomorrow and tomorrow's forecast, shows no error, and the later days come back on the next successful poll. The failure is logged once at info level when it starts and once when it is over.
- **Shorter error text in the log.** When a Wolta request fails with an HTTP error, the response body in the log message is cut to one line of at most 200 characters, so an HTML error page from a proxy no longer fills the log.
- **Bigger attribute, still not recorded.** `prices` now holds up to roughly 400 points. It stays excluded from the recorder, so it does not fill the database.
- **The plain *Spot price* sensor is unchanged**, and so are the Swedish-zones-only rule and the rest of the integration.
- **Source.** On the forecast sensor the `attribution` credits the forecast sources whenever any forecast day is present, also when only days 2 and 3 are left.
- **When it appears.** The forecast for days 2 and 3 is already live on wolta.se: it shows up on the first poll after you update, if the forecast sensor is enabled.
